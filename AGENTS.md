# AGENTS.md

Instructions for AI coding agents (Claude Code, Codex, Copilot, Cursor, ...) working on
this repository. Human contributors should read [CONTRIBUTING.md](CONTRIBUTING.md); the
rules below are the same, written for agents.

## Project

`advanced_webview` is a Flutter WebView plugin for **Android and iOS only**, built
on [Pigeon](https://pub.dev/packages/pigeon). It borrows feature ideas from
`flutter_inappwebview` but optimises for a small public API and maintainability.
Design rationale (Japanese): [doc/architecture.md](doc/architecture.md). Read it
before changing the architecture.

Do not add Web, macOS, Windows or Linux support.

## Layout

```
pigeons/messages.dart              Dart <-> native contract (single source of truth)
lib/advanced_webview.dart    Public API: only what is exported here is public
lib/src/controller.dart            MobileWebViewController (one controller = one WebView)
lib/src/widget.dart                MobileWebView (AndroidView / UiKitView)
lib/src/settings.dart              WebViewSettings (immutable)
lib/src/navigation.dart            NavigationRequest, WebResourceError, callback typedefs
lib/src/platform/messages.g.dart   GENERATED by Pigeon
lib/src/platform/event_dispatcher.dart  routes native -> Dart events by webViewId
android/src/main/kotlin/dev/k1t/advanced_webview/   Kotlin implementation
ios/advanced_webview/Sources/advanced_webview/ Swift implementation
ios/advanced_webview/Package.swift  Swift Package Manager manifest
ios/advanced_webview.podspec        CocoaPods spec (same sources as Package.swift)
test/                              Dart unit tests with a fake HostApi
example/                           Example app + integration_test
website/                           Docs site (VitePress), deployed to GitHub Pages by .github/workflows/docs.yml
```

## Commands

Flutter is managed with [FVM](https://fvm.app); the version is pinned in `.fvmrc`.
Always run Flutter and Dart through `fvm` (run `fvm install` once after cloning).
To upgrade Flutter, use `fvm use <version>` and commit `.fvmrc`; CI reads the same file.

```sh
fvm install                                     # install the pinned Flutter
fvm flutter pub get
fvm dart format $(git ls-files '*.dart' | grep -v '\.g\.dart$')
fvm flutter analyze
fvm flutter test
fvm dart run pigeon --input pigeons/messages.dart   # after editing pigeons/messages.dart
fvm flutter pub publish --dry-run                   # package validation
cd example && fvm flutter build apk --debug         # Android build check
cd example && fvm flutter build ios --simulator --debug  # iOS build check (macOS only)
cd website && npm ci && npm run dev                 # docs site preview (Node 22)

# Native lint / format (Pigeon output *.g.kt / *.g.swift is always excluded)
ktlint --format $(git ls-files '*.kt' '*.kts' | grep -v '\.g\.kt$')            # Kotlin
swift format --in-place $(git ls-files '*.swift' | grep -v '\.g\.swift$')      # Swift
swift format lint --strict $(git ls-files '*.swift' | grep -v '\.g\.swift$')
```

Run `fvm dart format`, `fvm flutter analyze` and `fvm flutter test` before finishing a change.
When you touch Kotlin or Swift, also run ktlint and swift-format as above.
If Flutter or a platform SDK is not available in your environment, say so instead of
claiming the change was verified; CI (`.github/workflows/ci.yaml`) builds both platforms.

## Hard rules

1. **Never edit generated files by hand**: `lib/src/platform/messages.g.dart`,
   `android/.../Messages.g.kt`, `ios/.../Messages.g.swift`. Edit `pigeons/messages.dart`,
   regenerate, and commit the generated output together with the change. CI fails when
   generated code is stale.
2. **Keep Android and iOS mirrored.** Both sides use the same file and class names
   (`MobileWebView`, `WebViewRegistry`, `WebViewHostApiImpl`, `MobileWebViewFactory`,
   `MobileWebViewPlugin`). When you change one platform, make the equivalent change on the
   other, or explain in the PR why the behaviour differs.
3. **The controller owns the WebView lifetime.** The native WebView is created via
   `HostApi.create` when `MobileWebViewController` is constructed and destroyed only by
   `controller.dispose()`. The platform view factory only looks up an existing instance by
   `webViewId`. Do not tie the WebView's lifetime to the widget.
4. **One HostApi / FlutterApi pair for all instances**, addressed by `webViewId`. Do not
   introduce per-view channels or hand-written `MethodChannel` code.
5. **Keep the public API small.** Add exports to `lib/advanced_webview.dart` only
   deliberately, document every public member with dartdoc, and record user-visible
   changes in `CHANGELOG.md` under `## Unreleased`.
6. Behaviour must match on both platforms unless documented: navigation decisions are
   main-frame only; JavaScript channels are exposed as `window.<name>.postMessage(String)`;
   JavaScript results are JSON-encoded natively and decoded in Dart (`undefined` -> `null`).
7. iOS builds with both Swift Package Manager and CocoaPods. Keep
   `ios/advanced_webview/Package.swift` and `ios/advanced_webview.podspec` in
   sync (minimum iOS version, sources, resources, dependencies). Swift sources live under
   `Sources/advanced_webview/`, resources under its `Resources/` folder. CI builds
   the example with each (`ios` and `ios-cocoapods` jobs).
8. Pigeon field names must not clash with Swift `NSObject` members (e.g. use `message`,
   not `description`).

## Testing

- Dart behaviour: unit tests in `test/` using `FakeHostApi` (`test/fake_host_api.dart`).
  Inject it via the `@visibleForTesting` `hostApi` / `dispatcher` constructor parameters.
- Native: Kotlin unit tests with Robolectric in `android/src/test/kotlin/`, Swift unit
  tests with XCTest in `example/ios/RunnerTests/`. Keep them mirrored like the sources.
- End-to-end: `example/integration_test/` (needs a device or simulator). CI runs it on an
  Android emulator and an iOS simulator; put behaviour that must match on both platforms here.
- Add or update tests for every behaviour change. Never skip or delete a failing test to
  make CI pass.

## Style

- Dart: `flutter_lints` (see `analysis_options.yaml`), `dart format` default width.
- Kotlin: official Kotlin style enforced by [ktlint](https://pinterest.github.io/ktlint/)
  1.8.0 (`ktlint_code_style = intellij_idea`, 4-space indent, 120 columns; see
  `.editorconfig`), coroutines (`suspend`) for async HostApi methods.
- Swift: Swift API Design Guidelines, formatted and linted by
  [swift-format](https://github.com/swiftlang/swift-format) (`swift format`, bundled with the
  Swift 6 toolchain / Xcode 16+; 2-space indent, 100 columns; see `.swift-format`).
  CI pins Swift 6.4.1; if a local version formats differently, follow the CI diff.
  `async` for async HostApi methods.
- CI (`kotlin-lint`, `swift-lint` jobs) fails on any ktlint or swift-format violation. Fix
  the code rather than disabling rules; if a rule must be disabled, do it in
  `.editorconfig` / `.swift-format` with a comment explaining why.
- Code comments and dartdoc in English. Docs under `doc/` may be Japanese.
- The docs site has English pages in `website/` and Japanese in `website/ja/`; keep them in
  sync, like README.md and README.ja.md. When a user-visible behaviour changes, update the
  matching guide page too.

## Pull requests

- Keep PRs focused on one topic and fill in `.github/pull_request_template.md`.
- Do not bump the package version or publish; releases are done by the maintainer by
  pushing a `vX.Y.Z` tag (`.github/workflows/publish.yml`).
- Do not commit secrets, signing configs, `pubspec.lock` of the root package, or
  `apm_modules/`.

## AI tooling (APM)

Agent configuration is managed with Microsoft's
[Agent Package Manager](https://github.com/microsoft/apm) (APM CLI 0.33.0):

- `AGENTS.md` (this file) is hand-written and is the source of truth for repo-wide rules.
  Do not regenerate it with `apm compile`.
- `apm.yml` pulls shared skills from [`imk1t/apm-shared`](https://github.com/imk1t/apm-shared)
  (`create-pr`, `code-docs`, `project-docs-sync`, `code-hygiene`) and declares MCP servers
  (`dart`, plus `context7` from apm-shared). These skills defer to the rules in this file.
- Project-specific skills live in `.apm/skills/` (e.g. `pigeon-contract`).
- `apm install` deploys skills to `.agents/skills/` and `.claude/skills/`, and MCP config to
  `.mcp.json` and `.codex/config.toml`. These outputs are git-ignored; only `apm.yml`,
  `apm.lock.yaml`, `apm-policy.yml` and `.apm/` are committed. Never edit the lock hashes by hand.
- `apm-policy.yml` is enforced in CI (`.github/workflows/apm.yml`) by the apm-shared verifier.

Setup after cloning, and after changing `apm.yml` or `.apm/skills/`:

Install the APM CLI with Homebrew. The lock and CI are pinned to APM 0.33.0, so check the
version; if Homebrew provides a different one, use the official installer pinned to it
(in CI or containers without Homebrew, `pip install apm-cli==0.33.0` also works):

```sh
brew install apm
apm --version                                   # must be 0.33.0
# otherwise: curl -sSL https://aka.ms/apm-unix | sh -s -- @v0.33.0
```

```sh
apm install --frozen --target agent-skills,claude,codex   # deploy from the committed lock
apm install --target agent-skills,claude,codex            # after changing apm.yml / .apm/: updates apm.lock.yaml
```

Commit `apm.lock.yaml` together with the change.
